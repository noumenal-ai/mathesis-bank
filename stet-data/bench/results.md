# Step 1g: measurements

Apple M4 Pro, macOS 15.6.1, Lean v4.31.0. Each file was run with `lean <file>` (via `bench/run.sh`),
sequentially, so runs did not compete for the CPU. Times are wall seconds for the whole file,
including importing `StetData`, which alone takes 0.63 s warm (`Bench_base.lean`). Peak is maximum
resident memory. **No Lean limit was raised:** `maxRecDepth` stayed at 512 and `maxHeartbeats` at
200000.

The plan's protocol, with two changes Dhruv approved: the data is a `List`, and the bound uses core's
`Dyadic`.

```lean
def S : List (Option Dyadic) := (f32bits% "<n>.f32").toList.map decode32
example : (S.filterMap id).sum < Dyadic.ofIntWithPrec 1 (-200) := by decide          -- and the other forms
```

The data is n uniformly random finite binary32 words (seed 20261007). The claim is true, since every
finite binary32 value is below 2^128 in magnitude.

## The plan's table

| n | `def S` alone | `.olean` of S | `decide` | `decide +kernel` | `rfl` on a Bool | failure mode |
|---|---|---|---|---|---|---|
| 10 | 0.71 s | 25,760 B | 0.70 s | 0.68 s | 0.67 s | none |
| 100 | 0.62 s | 144,560 B | fails | 0.70 s | fails | `decide`, `rfl`: recursion depth |
| 1,000 | 0.68 s | 1,332,560 B | fails | 1.17 s (1.4 GB) | fails | `decide`, `rfl`: recursion depth |
| 10,000 | fails | (none) | fails | fails | fails | `def S` itself: recursion depth |

Every failure is the same error, verbatim:

```
error: maximum recursion depth has been reached
use `set_option maxRecDepth <num>` to increase limit
use `set_option diagnostics true` to get diagnostic information
```

For `decide` and `rfl` it is reported at the tactic or the term. For `def S` at n = 10,000 it is
reported at the declaration's name: the failing step comes after the term is elaborated, and it is
code generation (see below).

## The kernel route: `noncomputable def S` and `decide +kernel`

`noncomputable def S` skips code generation, which no claim needs. The kernel sees the same term.

| n | `S` alone | `.olean` of S | `decide +kernel` | peak memory |
|---|---|---|---|---|
| 1,000 | ok | 205,328 B | 1.09 s | 1.4 GB |
| 10,000 | 0.77 s | 2,005,328 B | 7.36 s | 2.9 GB |
| 30,000 (probe) | | | 25.26 s | 6.4 GB |
| 100,000 (probe) | | | not finished at the 500 s cap | 9.6 GB when stopped |

The machine has 24 GB of memory, so the 100,000 run was stopped by time, not memory.

Probe data comes from its own seed (20261008); `python3 bench/mkbench.py --probe` regenerates it.
`decide +kernel` adds no axioms: a named version of the n = 1,000 claim depends on
`[propext, Quot.sound]`, as plain `decide` does.

## Classes (a) and (b) of the differential test, in the kernel

`tests/diff/KernelCheck.lean` (generated by `tests/diff/mkkernelcheck.py`) checks 3,078 words, all of
classes (a) and (b), against the C oracle's values, by plain `decide`, 12 words per theorem. All 257
theorems pass in 3.0 s wall (10.6 s CPU; Lean checks theorems in parallel), 631 MB peak, each
depending on `[propext, Quot.sound]`. Kernel evaluation of `decode32` therefore agrees with the
oracle on every structured case, as compiled evaluation does on every word.

## Reading: where it breaks, and why

1. **Plain `decide` and `rfl` stop at about 75 values.** Both evaluate in the elaborator before the
   kernel sees anything: `decide` reduces the `Decidable` instance with `whnf`, and `rfl` unifies with
   `isDefEq`. Both recurse once per list cell through `map`, `filterMap` and the `foldr` in
   `List.sum`, and the elaborator's recursion is capped by `maxRecDepth` (512). The kernel has no
   such cap, so `decide +kernel`, which skips the elaborator's evaluation, carries the same claim to
   30,000 values. **`decide +kernel` is the closing form for claims about data**, at no cost in
   axioms. Plain `decide` is for small checks.
2. **A compiled `def S` stops at 2,046 values, in code generation.** The compiler, also bounded by
   `maxRecDepth`, recurses through the literal list. Compiling the data also makes the `.olean` 6.5×
   larger (1.33 MB against 205 KB at 1,000 values) for code that no claim runs. **Data should be a
   `noncomputable def`.** It then costs about 200 bytes per value in the `.olean`, 50× the 4 bytes of
   the file.
3. **The kernel route grows faster than linearly, then falls off a cliff.** Net of the 0.63 s
   import, kernel time per value is about 0.46 ms at 1,000, 0.67 ms at 10,000 and 0.82 ms at
   30,000: 3.4× the time for 3× the values from 10,000 to 30,000. From 30,000 to 100,000 it is more
   than 20× for 3.3× the values (over 5 ms per value), with memory at 9.6 GB of 24 GB when stopped.
   Each value costs a decode plus one step of a running sum whose mantissa reaches about 280 bits,
   because the sum is aligned to exponents near −149. What causes the cliff is not identified; the
   likely suspects are the kernel's reduction caches and allocation as the term grows.
4. **The plan's open question (UU) now has an answer.** Data as a kernel term is the right primitive
   up to about 10^4 values (seconds), and it reaches 3 × 10^4 in under half a minute. 10^5 is out of
   reach on this machine. That is far from ML scale, where 10^6–10^9 values are normal. There, the
   kernel must check something smaller than the data: a certificate, or a sample chosen at random
   from committed data.

## Measurement notes

Runs that overlapped other work on the machine were discarded and repeated alone. Two of them moved:
- **30,000 values:** 32.45 s overlapped, 25.26 s alone.
- **Noncomputable 1,000 values:** a single run of 3.18 s came right after a 9.6 GB process was
  stopped. Back to back, the compiled and noncomputable versions take 1.16–1.25 s and 1.09 s.

Every number above is from a run on an otherwise idle machine.
